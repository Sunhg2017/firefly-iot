# Firefly IoT 平台能力补齐评审

## 1. 范围与结论

| 项目 | 内容 |
| --- | --- |
| 日期 | 2026-11-15（Asia/Shanghai） |
| 初始源码基线 | `dec3f11`，审查开始时 `master` 与 `origin/master` 一致，工作区干净 |
| 增量核对 | `ec34294` 模拟器日志及 `fb2a8d3` MQTT TLS/mTLS；后续并行开发不自动纳入本次结论 |
| 目标 | 识别平台还需要补充的能力，区分未闭环功能、未发现实现的能力及业务可选项 |
| 方法 | 对照控制器、业务服务、消息链路、迁移、部署、CI 和已有设计/运维文档进行静态核查 |
| 边界 | 不修改业务实现；不将历史审计结论直接套用到当前版本；不替代修复验收、真实依赖联调、压测或生产认证 |

**总体判断：基础功能覆盖已较完整，下一阶段优先补“可靠执行、身份生命周期、灾难恢复和规模治理”，而不是继续增加孤立菜单或协议名称。**

评审以通用多租户 IoT 平台为默认视角；不假定一定要做公共 SaaS、工业边缘平台或行业数字孪生。商业计费、边缘运行时、行业资产模型应由目标客户决定，不能都当成通用上线前置条件。

## 2. 已有能力：不应再列为缺失

| 能力 | 本次看到的实现 | 当前判断 |
| --- | --- | --- |
| 设备接入 | MQTT、HTTP、CoAP、TCP/UDP、WebSocket、Modbus、SNMP、LoRaWAN，自定义协议解析及调试 | 已有广泛接入覆盖；重点转向协议一致性和生产运行边界 |
| 设备与模型 | 产品、设备、分组/动态分组、标签、拓扑、物模型、影子 | 已有基础设备管理；尚需生命周期与数据契约深化 |
| OTA 与配置 | 固件任务、逐设备进度、升级指令、远程配置版本及回滚 | 已有可执行基础，不再是只有元数据；发布安全闭环仍需补齐 |
| 消息与数据可靠性 | Kafka 重试/DLT、topic 初始化、Kafka HA 编排、离线下行队列、desired 落库、遥测去重与 payload 单存 | 已有基础机制；不等于业务动作可恢复、可重放且不重复执行 |
| 数据治理 | 保留策略、降采样、归档、连续聚合缺口补刷 | 已有存储治理；仍需数据质量、事件时间和模型版本治理 |
| 告警与外部协同 | 告警、通知重试、数据流转、事件订阅、跨租户共享权限/限流/有效期 | 已有流程；可靠回执、失败修复和行业处理闭环仍需深化 |
| 安全与租户 | 工作空间、RBAC/数据范围、AppKey OpenAPI、会话、审计、设备证书登记、SAS 与传输层 mTLS | 不再以“没有权限/没有审计/没有 mTLS”概括；证书到设备身份的绑定与管理安全需单独完善 |
| 可观测性 | Prometheus、Grafana、Alertmanager、消息/设备/规则/OTA 指标 | 已有指标栈；还需面向业务成功的 SLO 与故障定位链路 |
| 测试工具 | 设备模拟器、场景编排、批量创建设备、多协议压测和报告 | 已有压测工具；尚不能据此推断容量或故障恢复承诺已验证 |

依据包括当前源码及 [消息与数据可靠性](../design/message-data-reliability.md)、[OTA](../design/ota-upgrade.md)、[可观测性](../design/observability.md)、[共享与连接器补齐](../design/shared-data-and-connector-remediation.md)、[模拟器说明](../../firefly-simulator/README.md)。文档中的“Done”只代表原交付声明，本评审不把它等同于生产验收结论。

## 3. 优先级总表

优先级表示实施顺序，不是已经复现的安全漏洞等级；每项都需要按实际部署与客户合同确定边界。

| 编号 | 建议能力 | 现状类型 | 建议顺序 |
| --- | --- | --- | --- |
| CAP-01 | 统一指令回执与可恢复设备作业 | 已有入口，执行闭环不足 | 生产控制设备前 |
| CAP-02 | 设备可信身份及凭据全生命周期 | 已有 mTLS 与登记/认证分支，设备身份绑定及生命周期不足 | 生产接入前，尤其声明 X.509 时 |
| CAP-03 | 固件供应链与分批升级治理 | 已有 OTA，完整性和发布控制不足 | 批量 OTA 前 |
| CAP-04 | 备份恢复、容灾与部署高可用 | Kafka 有 HA；全平台恢复能力缺少证据 | 承诺生产可用性前 |
| CAP-05 | 失败消息修复与副作用幂等 | 已有 DLT，运营修复闭环不足 | 依赖可靠消息交付前 |
| CAP-06 | 多租户数据面资源治理 | 已有局部限流，统一资源保护不足 | 多租户规模运行前 |
| CAP-07 | 数据质量与物模型版本治理 | 已有模型和存储，数据契约不足 | 下一阶段基础能力 |
| CAP-08 | 设备级可观测性与业务 SLO | 已有指标栈，跨链路定位不足 | 与 CAP-01/04/05 同步 |
| CAP-09 | 设备 SDK、协议契约和开发者接入包 | 文档/模拟器/插件 API 已有，设备 SDK 未发现统一交付 | 多厂商接入前 |
| CAP-10 | 管理安全、密钥治理与数据退出 | 已有鉴权/审计，生命周期治理不完整 | 按生产安全要求分阶段 |
| CAP-11 | 可重复交付与自动化验收门禁 | CI 编译/单测已有，场景和供应链门禁不足 | 生产版本发布前 |

以下章节记录每项的代码依据、最小补齐范围与验收方法；业务条件型能力单独列示，避免把可选功能误当作硬性缺陷。

## 4. 建议优先补齐的能力

### CAP-01 统一指令回执与可恢复设备作业

**现有依据：** [DeviceMessageController](../../firefly-device/src/main/java/com/songhg/firefly/iot/device/controller/DeviceMessageController.java#L37) 的控制接口发起发送后返回 `R<Void>`；[DeviceBatchOperationService](../../firefly-device/src/main/java/com/songhg/firefly/iot/device/service/DeviceBatchOperationService.java#L126) 逐设备调用生产者并统计成功；[RemoteConfigService](../../firefly-device/src/main/java/com/songhg/firefly/iot/device/service/RemoteConfigService.java#L229) 发起发送后标记 `DELIVERED`。这些调用没有统一返回供用户跟踪设备最终执行结果的指令标识。OTA 和远程配置已有各自状态表，不应另行把它们当作完全缺失。

**需要补齐：** 建立统一的业务作业与指令记录，明确“接受请求、等待投递、已发送、设备已接收、执行成功、失败、超时、取消”等状态；按设备持久记录尝试次数、有效期、回执、错误和操作者。批量操作需要目标快照、并发上限、暂停/取消、失败重跑及进程重启后的认领机制。复用任务中心的查询与通知，业务执行状态由明确的工作进程维护，避免每个模块重复实现一套不可恢复的线程池任务。

**为什么优先：** 目前业务侧“发起发送成功”不能回答设备是否实际执行。它会直接影响设备控制、远程配置、OTA 和客户工单。

**最小验收：** 设备离线后上线、发送进程重启、重复回执、超时回执均能收敛到可解释的终态；同一指令不会重复产生设备副作用；批量失败能仅重跑失败目标，取消后不再启动新的目标。明确区分 Broker 确认和设备业务执行回执。

### CAP-02 设备可信身份及凭据全生命周期

**现有依据：** [DeviceCertificateService](../../firefly-device/src/main/java/com/songhg/firefly/iot/device/service/DeviceCertificateService.java#L44) 已有证书登记、吊销和指纹状态校验；但 [DeviceCredentialService](../../firefly-device/src/main/java/com/songhg/firefly/iot/device/service/DeviceCredentialService.java#L75) 的 X509 分支把传入的 `deviceSecret` 当作指纹检查。[EmbeddedMqttAuthenticator](../../firefly-connector/src/main/java/com/songhg/firefly/iot/connector/protocol/mqtt/EmbeddedMqttAuthenticator.java#L17) 仍接收用户名/密码。增量提交 `fb2a8d3` 已通过 [FireflyMqttSslContextCreator](../../firefly-connector/src/main/java/com/songhg/firefly/iot/connector/protocol/mqtt/FireflyMqttSslContextCreator.java#L54) 和 [Broker 配置](../../firefly-connector/src/main/java/com/songhg/firefly/iot/connector/protocol/mqtt/EmbeddedMqttBroker.java#L73) 增加可配置的传输层 mTLS、独立 truststore 和 TLS 版本限制；不能继续认定平台没有客户端证书校验。但所查链路尚未把握手中已证明的证书身份绑定到所声明的设备，[该次设计说明](../design/mqtt-tls-mutual-auth.md) 也明确将设备身份绑定、在线签发及 CRL/OCSP 排除在交付范围之外。

**需要补齐：** 将传输层已验证的客户端证书与平台设备身份、租户和授权范围绑定；在其他声明支持 X.509 的入口提供等效认证或经过明确设计的私钥挑战证明。由受信任上下文取得身份，不能把客户端自报指纹当作该设备的身份凭证。补充生产烧录/初始注册、受控激活、证书签发或导入信任策略、到期预警、续期、轮换、撤销后断开会话、报废和返修换件流程。密钥应有明确的生成与保管责任，不要求把设备私钥统一交给平台。

**最小验收：** 只知道设备证书/指纹而没有对应私钥不能登录；同一受信任 CA 下，设备 A 的证书不能冒用设备 B 的身份；过期或吊销凭据不能继续建立会话，已建立会话的处置符合策略；轮换全过程可审计；制造批次泄露或返修设备可定向撤销而不影响其他设备。平台实现与设备固件配合验收，本轮未执行真实 TLS 握手或身份冒用测试。

### CAP-03 固件供应链与分批升级治理

**现有依据：** [OtaService.verifyFirmware](../../firefly-device/src/main/java/com/songhg/firefly/iot/device/service/OtaService.java#L139) 检查摘要格式及可选摘要签名，未在该流程读取固件文件重新计算摘要；任务创建展开设备后逐一发送，灰度按比例截取目标。[现有设计风险](../design/ota-upgrade.md) 已说明文件级校验、分批推进/暂停以及数据库与发送事务边界的不足。

**需要补齐：** 从实际对象内容计算并校验文件长度、摘要和签名；将产品/硬件版本、目标版本、最低可升级版本、签名密钥标识纳入发布清单。补齐小批试升、健康观察、失败率停止、维护时窗、并发控制、暂停与恢复；对发送与任务记录使用可靠交付机制。按设备能力设计失败回滚、断电恢复与防降级策略，平台不能单方面承诺固件侧尚未实现的能力。

**最小验收：** 文件被替换或损坏、硬件型号不匹配、签名不合法均不能发布；首批失败超过配置门槛后不再下发后续批次；中途断电/断网后状态可恢复；回滚后的实际版本和健康状态可查询。不要把“灰度比例筛选”写成已经具备自动灰度发布。

### CAP-04 备份恢复、容灾与部署高可用

**现有依据：** [生产 Compose](../../deploy/docker-compose.prod.yml) 有持久卷与监控服务；[Kafka HA overlay](../../deploy/docker-compose.kafka-ha.yml#L1) 已有三个 Broker。三个容器仍由同一 Compose 部署，不能证明跨宿主机故障隔离。对 `deploy/`、CI、运维文档的检索未发现完整的数据库/对象存储备份恢复自动化、时间点恢复或恢复演练材料；不能排除部署方在仓库之外已有托管方案。

**需要补齐：** 明确 PostgreSQL/TimescaleDB、Redis 权威状态、MinIO 对象、密钥、配置和消息位点各自的恢复策略；备份加密、异地保留、恢复校验与自动演练；为每类业务定义可接受数据损失窗口和恢复时间。根据部署目标选择托管 HA 或跨故障域实例，补充滚动升级、实例退出排空、迁移检查与版本回退流程。无需为了这一目标强制引入 Kubernetes。

**最小验收：** 在独立环境从备份恢复，并核对设备身份、遥测、固件文件及配置引用；模拟宿主机丢失而非仅重启一个容器；记录实际恢复时间与数据缺口。没有演练数据前不承诺固定 SLA/RTO/RPO。

### CAP-05 失败消息修复与副作用幂等

**现有依据：** [KafkaConsumerErrorConfig](../../firefly-common/src/main/java/com/songhg/firefly/iot/common/kafka/KafkaConsumerErrorConfig.java#L34) 已有有限重试及 DLT；[Kafka 可靠性文档](../design/kafka-reliability.md) 明确 DLT 仍需人工或后续工具重投。[EventSubscriptionRuntimeService](../../firefly-rule/src/main/java/com/songhg/firefly/iot/rule/dataforward/service/EventSubscriptionRuntimeService.java#L66) 和 [DataForwardRuntimeService](../../firefly-rule/src/main/java/com/songhg/firefly/iot/rule/dataforward/service/DataForwardRuntimeService.java#L78) 对单目标失败记录统计/日志后继续，没有看到逐条投递结果的持久重投任务。现有能力不能统一解释成可靠外部交付。

**需要补齐：** 消息检索、失败原因分类、原始报文隔离、按租户/目标审批重放、限速重放、毒消息隔离、投递历史和修复审计；对可靠事件使用 outbox 或等效持久投递机制。幂等键必须覆盖事件、规则版本、目标和动作，而不只覆盖遥测入库。外部 Webhook/通知需明确可靠投递或尽力投递的产品契约。

**相关下行缺口：** [DownlinkPendingQueue](../../firefly-connector/src/main/java/com/songhg/firefly/iot/connector/protocol/downstream/DownlinkPendingQueue.java#L43) 入队失败只记录日志；队列有裁剪和整体 TTL；[DownlinkPendingFlusher](../../firefly-connector/src/main/java/com/songhg/firefly/iot/connector/protocol/downstream/DownlinkPendingFlusher.java#L30) 在重连事件中取一批后发送。还应定义超限/过期的业务终态、取出后进程退出的恢复以及持续补发机制，不把 Redis 队列当作已经具备完整指令记录。

**最小验收：** 消费后进程退出、外部目标超时、部分动作成功后重试、积压超限均不静默消失；重放不会再次执行已成功的高风险动作；每条失败可定位到设备、目标、尝试和最终处置。

### CAP-06 多租户数据面资源治理

**现有依据：** [AuthGlobalFilter](../../firefly-gateway/src/main/java/com/songhg/firefly/iot/gateway/filter/AuthGlobalFilter.java) 已有 AppKey/OpenAPI 配额，跨租户共享也已有频率限制；[MqttProperties](../../firefly-connector/src/main/java/com/songhg/firefly/iot/connector/config/MqttProperties.java#L38) 有消息大小限制。所查主设备接入与执行链路未体现统一的按租户连接数、上行速率、字节吞吐、规则计算预算、任务并发及查询成本控制。

**需要补齐：** 按租户/产品/设备分层限制连接、上报、重连风暴和请求积压；控制规则计算、导入导出、OTA 并发和大范围查询；用公平调度、背压、拒绝原因和用量指标避免一个租户挤占所有服务。区分保护阈值与商业套餐。

**重要取舍：** [套餐/配额下线设计](../design/tenant-plan-quota-removal.md) 明确旧模型已被主动删除。本评审不建议恢复旧页面、旧表或备用逻辑；资源保护是运行安全能力，是否收费是独立商业决定。

**最小验收：** 一个租户突发高负载时，另一个租户的约定请求仍能在目标时延内处理；超限反馈可解释；断连重连不会绕过限制；规则和后台任务不会耗尽公共执行器。具体容量数字应由负载模型和压测决定。

### CAP-07 数据质量与物模型版本治理

**现有依据：** [ProductService.updateThingModel](../../firefly-device/src/main/java/com/songhg/firefly/iot/device/service/ProductService.java#L203) 已限制已发布物模型只能追加定义，不能说模型完全没有变更约束。但 [DeviceDataService](../../firefly-device/src/main/java/com/songhg/firefly/iot/device/service/DeviceDataService.java#L149) 的遥测路径按值类型落库，未见在该链路应用物模型范围/枚举/单位校验；[MessageCodec](../../firefly-connector/src/main/java/com/songhg/firefly/iot/connector/protocol/MessageCodec.java#L48) 的标准 JSON 入口使用接收时的系统时间。

**需要补齐：** 发布不可变模型版本并记录设备适用版本、校验规则和变更影响；保留事件发生时间与平台接收时间两个字段，定义乱序、迟到、设备时钟偏差的处理；支持类型/范围/枚举校验、单位转换、质量标记和无效数据隔离。版本管理应服务真实的多固件设备群，不能为了迁就旧内部接口添加隐式兼容分支。

**最小验收：** 非法枚举、错类型、单位不一致、离线补传、时钟异常不会污染正常分析而不留痕；能够解释某条数据依据哪个模型版本入库；模型升级前能评估受影响设备和规则。

### CAP-08 设备级可观测性与业务 SLO

**现有依据：** [observability 设计](../design/observability.md) 明确集中日志和链路后端未纳入当前交付；[告警规则](../../deploy/observability/alerts.yml) 已覆盖服务可用、HTTP 5xx、JVM、消息/规则失败和无设备在线，但并非指令回执与数据完整性的完整观测。

**需要补齐：** 以业务指令 ID、消息 ID、设备业务标识关联接入、处理、规则、下行与回执；建设日志/链路查询及受控设备诊断包。补齐 Kafka lag、DLT 积压、待投递最老年龄、回执超时、遥测新鲜度、数据缺口、租户延迟和错误预算告警。高基数设备标识放在可查询日志或追踪中，避免全部作为指标标签。

**最小验收：** 运维从一条“设备未执行”或“数据缺失”的工单能定位失败阶段，而不是依次登录全部容器；业务 SLO 统计能区分接收成功、处理成功和最终设备执行成功；告警能够实际送达值班渠道。

### CAP-09 设备 SDK、协议契约和开发者接入包

**现有依据：** 已有 [租户 OpenAPI 文档中心](../design/open-api-tenant-doc-center.md)、签名/curl 示例、[设备模拟器](../../firefly-simulator/README.md) 和 [服务端协议插件 API](../../firefly-plugin-api/pom.xml)。对仓库模块及交付文件的核查未发现可作为统一产品发布的设备端 SDK；服务端插件 API 不等同于嵌入式设备 SDK。

**需要补齐：** 先选目标客户真实使用的一到两种设备技术栈，提供版本化设备协议与参考实现：注册、认证/轮换、重连退避、离线缓存、消息 ID、时间同步、下行幂等、回执和 OTA 上报。给出协议兼容性测试向量、能力协商及最小接入示例。开放 API 增加面向合作方的契约变更检测、Webhook 验签/重试约定和可重复沙箱样例。

**最小验收：** 新厂商按公开接入包即可完成上报、下行与 OTA 测试；无需从模拟器代码反向理解协议。断网、时钟偏差、重复消息、凭据过期等场景有自动化用例。不要仅为“SDK 数量”同时启动多个语言版本。

### CAP-10 管理安全、密钥治理与数据退出

**现有依据：** 当前有登录/会话/权限/审计，且 [AppKeySecretCryptoService](../../firefly-system/src/main/java/com/songhg/firefly/iot/system/service/AppKeySecretCryptoService.java#L22) 已对 AppKey 密钥做加密，不能泛称所有密钥均未加密。对认证实现的定向核查未发现 MFA/二次授权流程；[TenantService.deactivateTenant](../../firefly-system/src/main/java/com/songhg/firefly/iot/system/service/TenantService.java#L286) 实施停用与租户记录删除，不等同于已经验证跨数据库、对象存储和缓存的数据退出。

**需要补齐：** 管理员 MFA 或由企业身份提供方强制实施、危险操作二次验证及按客户要求的审批；设备/AppKey/内部服务/固件签名密钥的独立生命周期、托管存储、轮换与紧急撤销；明确生产配置无默认秘密的检查。建立租户退出任务，覆盖凭据禁用、设备处置、数据导出/删除、文件清理、保留要求和可核验执行记录。受控安全审计导出需要脱敏、留痕及访问范围校验。

**最小验收：** 高权限账号泄露、单个密钥泄露、租户停用均有可执行处置步骤；轮换不会长期保留失效凭据；租户退出后列出实际删除与依法/依约保留的数据。具体法定要求应由业务与合规方确认，本评审不作法律判断。

### CAP-11 可重复交付与自动化验收门禁

**现有依据：** [CI](../../.github/workflows/ci.yml#L40) 已执行 Maven verify、前端类型检查/构建及镜像构建，发布 tag 触发部署。仓库已有大量单测、前端 API 烟雾脚本和模拟器压测，但所查流水线未发现真实依赖集成测试、浏览器关键路径、故障注入、SBOM 或依赖/秘密扫描门禁。不能用本次静态审查宣称这些检查已执行。

**需要补齐：** 用可重复的 PostgreSQL/TimescaleDB、Redis、Kafka、MinIO 环境跑核心场景；校验 Flyway 全新建库与升级；加入权限矩阵、上报到查询、控制到回执、OTA、取消/重启、DLT 重放的回归。将模拟器的负载与报告纳入容量基线，补充依赖/镜像扫描、秘密扫描、SBOM、发布清单和回滚验证。

**最小验收：** 版本发布能提供源码提交、镜像摘要、迁移版本、测试结果及容量/恢复测试记录；任一关键业务链断裂时阻止发布；历史验收探针转为持续测试，而非只保存一次通过截图。

## 5. 按目标市场选择的扩展

| 扩展方向 | 适用前提 | 建议补充 | 暂缓条件 |
| --- | --- | --- | --- |
| 边缘运行时与云边协同 | 工厂/园区弱网、现场必须脱网运行 | 受管边缘节点、采集配置下发、本地持久缓存/规则、断网自治、恢复补传、节点升级与资源观测 | 云端直连设备且无需离线自治时不必先做；目前 connector 多协议接入不能直接等同于完整边缘产品 |
| 行业资产与运维工单 | 客户需要设备映射产线、建筑、车辆、站点等资产 | 在已有分组/拓扑/地理围栏上增加行业资产关系、维修/校准/巡检、告警派单与处置回写 | 尚未选定行业前，不建设通用“大而全数字孪生” |
| 高级流分析 | 需要跨设备关联、时间窗口、多事件序列或预测 | 先落地事件时间/质量，再按场景选择窗口聚合、关联规则或外部流处理/分析集成 | 当前单设备阈值与普通规则已满足场景时不另建流计算平台 |
| SaaS 商业化计量 | 明确按租户收费且有计费指标与合同 | 用量计量、账单依据、套餐权益和运营流程，复用 CAP-06 的事实指标 | 私有部署/项目交付不应强制做计费；不得恢复已下线旧套餐代码 |
| 特定行业协议 | 已有目标设备和真实接入需求 | 对应厂商协议/行业协议适配、测试向量和运维支持 | 不仅为增加协议名称而实现；优先完成现有协议认证、断网和可靠性验收 |

其中边缘/行业能力的“未发现统一产品实现”结论只针对当前仓库，不代表无法通过现有平台集成外部产品完成。

## 6. 建议实施顺序

1. **第一批：形成可信且可恢复的最小生产闭环。** CAP-01 指令/任务记录、CAP-02 身份证明、CAP-04 恢复方案、CAP-05 失败修复优先；CAP-08 可观测性与 CAP-11 回归门禁同步建设。准备批量升级时将 CAP-03 纳入这一批。
2. **第二批：支撑多租户和多厂商规模运行。** 完成 CAP-06 资源保护、CAP-07 数据契约、CAP-09 接入 SDK；CAP-10 按生产安全要求实施，管理员强认证和生产密钥要求不应等到规模化后才处理。
3. **第三批：按客户需求增加行业能力。** 从边缘、工单/资产、流分析、SaaS 计费中选择真实需求，避免五条产品线同时展开。

建议先定义共享的 `指令/作业标识、状态、幂等、回执、失败处置、事件时间`，再改各业务模块。不要先增加一个“任务菜单”，却让 OTA、远程配置、批量操作仍各自维护互不一致的执行语义。这不要求拆出新微服务，优先复用现有模块并明确权威数据归属。
